1. Executive summary

EduMate Pro has been built from an empty product idea to a working, multi-tenant school platform. The system now supports a platform Super Admin who onboards schools and appoints the people who run them, and each school then operates independently: its own staff, learners, classes, subjects, academics, fees, calendar, messaging and email configuration.

All eleven functional areas requested to date are implemented and verified — the codebase passes static analysis with zero issues, its unit tests pass, and it compiles to a production web release.

2. Roles and access model

RoleScopeWhat they can do
Super Admin Platform, above all schools Create and suspend schools; assign each school's admins and principals by phone number; search across schools.
School Admin One or more schools Full management of their school(s): staff, learners, classes, subjects, applications, payments, fees, broadcasts, calendar, chat approvals, email settings, progress reports.
Principal One or more schools Same management rights as School Admin (documented assumption: principals lead the school and are not given fewer powers than the office admin).
Teacher One or more schools Their classes and subjects; capture marks; publish lesson plans and homework; scan attendance; staff chat; parent chat once approved.
Parent One or more schools Apply for a child, track the application, view child progress, homework and lesson plans, submit payments with proof, request a teacher chat, receive announcements.
Multi-school by design. Membership lives at schools/{schoolId}/members/{uid}. A single person can hold a different role at each school; one collection-group query returns every school they belong to, which powers the in-app school switcher. Admins, principals and teachers assigned to several schools see all of them and switch with one tap.

4. Architecture

Technology

  • Client: Flutter (single codebase → Web, Android, iOS), go_router for routing with role guards, Provider for state.
  • Backend: Firebase — Phone Auth, Cloud Firestore, Cloud Storage. No server component: Cloud Functions were deliberately removed; SMTP email is sent from the app using each school's own configured credentials.
  • Security: Firestore rules enforce every boundary server-side — membership-based access per school, role checks for management actions, draft-only parent edits, participant-only chat, approved-thread-only messaging, and no self-escalation of roles.

6. Deployment checklist

  1. Create a Firebase project; enable Phone authentication and allow the SMS region (e.g. +27).
  2. Run flutterfire configure; deploy rules and indexes with firebase deploy --only firestore,storage.
  3. Bootstrap the first Super Admin: sign in once, then set users/{uid}.superAdmin = true in the console.
  4. Super Admin creates the first school and assigns its admin/principal.
  5. That admin configures the school's SMTP details in Email settings and sends a test message.
  6. Build and host: flutter build web --release then firebase deploy --only hosting.

7. Open items and risks

Web + SMTP. Browsers cannot open SMTP sockets. Email triggered from the web app is queued in an outbox and delivered when any staff member next uses the Android/iOS/desktop app. If a school will only ever use the web, a small mail relay (or restoring a single Cloud Function) would be needed for immediate delivery.
SMTP credentials are stored in Firestore and readable by that school's staff, because the app itself sends the mail. Use a dedicated no-reply mailbox / app password per school rather than a shared corporate account.
  • Push notifications — broadcasts are in-app + email; true device push needs a server component.
  • Search scale — client-side matching is right for a school-sized dataset; a search index would be needed at very large scale.
  • Reporting exports — progress reports are on-screen; PDF/printable report cards are a natural next step.
  • Testing depth — add widget tests for the wizard, mark capture and rules tests via the Firebase emulator before pilot.
  • Localisation — English only in this iteration.

8. Recommended next phase

  1. Pilot with one school on a live Firebase project (2–3 weeks).
  2. Add printable/PDF report cards and fee statements.
  3. Firebase emulator rule tests + widget tests for the critical flows.
  4. Decide on push notifications (requires a minimal server or FCM integration).
